# demo-app — Jewelry Order Management

A small 3-tier app, built specifically for Lesson 03's extended security/cloud
demo — deliberately **not** reusing Lesson 02's Tic-Tac-Toe app, so this
lesson's infrastructure doesn't get tangled up with Lesson 02's.

```
client/   static HTML/JS + nginx — the only public-facing piece
server/   Flask REST API — order logic + Postgres access
scripts/  deploy_service.py — the actual ECS deploy step Jenkins runs
terraform/
  shared/            2 ECR repos (applied once, by the instructor)
  modules/environment/  the full per-environment stack (VPC, ECS, IAM, Secrets Manager, ...)
  dev/ , prod/       two tiny root configs that each call the module once — two environments, one piece of module code
Jenkinsfile.dev
Jenkinsfile.prod
```

## Architecture

```
 internet
    |
    v
 [client]  (public, port 80)
    |  nginx reverse-proxies /api/ -> server.jewelry.local:5000
    v
 [server]  (NOT public — reachable only from client's security group)
    |  talks to db.jewelry.local:5432
    v
 [db]      (NOT public — reachable only from server's security group)
```

Every service runs as its own ECS Fargate task. All three technically have a
public IP (needed so Fargate can pull images from ECR and ship logs to
CloudWatch without a NAT Gateway or VPC endpoints — both cost extra and add
complexity this course doesn't need). What actually stops `server` and `db`
from being reachable from the internet is the **security group**, not the
absence of a public IP — the same least-privilege principle as the IAM
policies in this lesson, applied to the network instead.

Service-to-service calls (`client` -> `server`, `server` -> `db`) use **AWS
Cloud Map** private DNS (`server.jewelry.local`, `db.jewelry.local`) instead
of IP addresses, since a Fargate task's IP changes on every deployment.

## Two environments, full isolation

`dev` and `prod` each get their **own VPC** — not just separate naming, a
completely separate network. The only thing they share is the **ECR
registry** (`terraform/shared/`): images are built once and the same
artifact is tagged and pushed per environment, rather than rebuilding
per-environment infrastructure for something that's really just a package
store.

Each environment also gets its **own IAM deploy user**
(`jenkins-deploy-dev` / `jenkins-deploy-prod`), scoped to only that
environment's ECS cluster and the two shared ECR repos. A leaked dev
credential cannot touch prod.

## Secrets

The database password is never typed anywhere, never committed, and never
appears in a task definition. It's generated by Terraform
(`random_password`), stored in AWS Secrets Manager, and injected into the
`server` and `db` containers at startup via the ECS task definition's
`secrets` block — the infrastructure-layer equivalent of the Jenkins
Credentials Store from earlier in this lesson.

## Deploy model: Terraform provisions, Jenkins deploys

Terraform (`terraform/dev/`, `terraform/prod/`) creates the *shape* of the
infrastructure — run manually, once, by whoever has broad AWS permissions
(not by Jenkins). After that, each Jenkinsfile deploys new images by calling
`scripts/deploy_service.py`, which only registers a new ECS task definition
revision and updates the service — it never touches Terraform. That split is
what lets the Jenkins deploy users have such a narrow IAM policy: they never
need permission to create or modify infrastructure, only to ship a new image
into infrastructure that already exists.
